## Final state (implemented behavior)

- `repoise-core::store`: SQLite (WAL) with FTS5; transactional generation publication
  (`generation`/`file`/`chunk`/`chunk_fts`/`kv` tables), retention of the current plus
  the previous generation, `current_generation` and `load_generation` (records of the
  currently published generation, used by an in-progress build for reconciliation).
- `repoise-core::chunk`: structural chunkers for Markdown/MDX (`markdown`), plain
  prose `.txt/.rst/.adoc` and the fallback (`text`), and readable config formats
  (`config_fmt`, TOML/JSON/YAML). Oversized units split into labeled children with
  repeated context, exact 1-based line ranges and parent references.
- `repoise-core::indexing::index`: incremental build — unchanged files/chunks are
  reused by identity, changed files are reparsed, deleted files are tombstoned in the
  new generation; publishes one complete generation per scope and writes the
  versioned `state.json` manifest. Known secret shapes are redacted from stored chunk
  text (defense-in-depth; discovery already skips such files).
- `repoise-core::search`: offline lexical search (BM25 + explainable
  path/heading/role boosts), per-file diversity cap, bounded output, opaque
  continuation cursors bound to scope/query/filters/generation, and a
  lexical/filesystem fallback response for no matches.
- `repoise-core::read`: exact read-back of one opaque source id, re-reading the file
  at the snapshot and validating both the file content hash and the chunk text hash;
  any mismatch is a `Stale` diagnostic. GitHub permalinks only for a validated
  `github.com/<owner>/<repo>` remote plus a `git:<40-hex>` revision.
- `repoise-core::status`: scope, snapshot, index, freshness
  (`fresh`/`stale`/`unknown`), cache and config diagnostics in one view.
- `repoise-core::purge`: removes generated cache data only (one scope directory or
  the whole generated layout), validating opaque scope ids before touching paths.
- CLI: `index`, `status`, `search --query` (+ `--path-filter`, `--role`,
  `--max-results`, `--max-output-tokens`, `--cursor`), `read --source-id`,
  `purge --all | --repo-id <ID> --worktree-id <ID>`, all with `--json`. Exit codes:
  0 success, 1 operational failure, 2 usage, 3 missing/stale index (search/read/status).
  Freshness checking lives in `status` (exit 3 when the index is missing or stale);
  `check --fresh` and `index --paths` scheduling hints from the proposal are not
  separate commands in this PR.
- Tests: `crates/repoise-core/tests/v1_1.rs` (chunkers, store publication/retention,
  end-to-end index/search/read over the fake adapter, incremental reuse, stale reads,
  cursor binding, secret handling, status freshness, purge safety) and CLI
  integration tests in `crates/repoise-cli/tests/cli.rs`.

## Scope

Deliver the first offline docs milestone: install, init, index, search, exact read — no
vectors, no history, no MCP, no watch.

- Persistent SQLite metadata + FTS5 storage with transactional generation publication.
- Structural prose chunking (Markdown/MDX, .txt/.rst/.adoc, relevant config).
- Lexical search and exact reads with expected-hash validation.
- Incremental chunk reconciliation and freshness checking (`check --fresh`).
- `purge` for a repo scope.
- CLI JSON operations for search/read/status (the same service methods MCP calls in PR 6).

Out of scope: embeddings/hybrid (PR 3), code grammars (PR 4), history (PR 5),
watch/MCP/overlay beyond what exists (PR 6).

## Storage contract (master plan sections 3, 6)

- SQLite metadata and FTS5; local-first, no service. Inspect SQLite FTS5 support in
  doctor; fail clearly if absent. Account for SQLite WAL/SHM sidecars.
- Use a local disk, not a shared live network database; export via a consistent
  backup/checkpoint operation rather than copying an actively written database file
  alone.
- Illustrative layout under the platform user cache root (XDG cache on Linux,
  Library/Caches on macOS, LocalAppData on Windows), resolved through a tested platform
  adapter:

| Path | Contents |
| --- | --- |
| `repoise/repos/<repoId>/worktrees/<worktreeId>/index.sqlite` | Source manifests, snapshot/generation metadata, chunks, symbols/edges, FTS, optional vectors |
| `repoise/repos/<repoId>/embedding-cache/` | Optional shared content-addressed vectors, isolated within the repository/access scope (PR 3) |
| `repoise/repos/<repoId>/worktrees/<worktreeId>/state.json` | Versioned integration manifest and refresh diagnostics; database remains canonical |
| `repoise/repos/<repoId>/worktrees/<worktreeId>/tmp/` | Disposable build/import/export staging |

- Database table boundaries distinguish docs/config/code/history; separate physical
  databases are not required.
- Repo identity binds the actual local root/access scope; identical remote URLs must not
  merge independent private clones. Worktree identity separates branch/dirty state.
  Root moves require explicit rebind or rebuild.
- An explicit ignored project-local cache directory is supported for containers/portable
  workflows. Cache paths cannot affect the eligible source corpus. Commit config,
  integration scripts, and curated docs; do not commit generated SQLite/vector indexes
  or refresh them in pre-commit by default.
- Cache retention/size ceilings and status/purge cover source text storage from this PR
  onward.

## Chunking (master plan section 5)

- Parse Markdown structurally so headings inside fenced code are not headings. Preserve
  heading ancestry, links, adjacent explanatory paragraphs, lists, tables, and fenced
  blocks.
- For .txt/.rst/.adoc and config formats, use the appropriate structural/paragraph
  splitter with source offsets.
- Aim initially at 300–700 tokens, hard ceiling 1,000 or the provider input limit if
  smaller. Character count is only an estimate until a tokenizer/profile is configured.
- Large tables/code blocks require labeled splits with repeated header/context, exact
  ranges, and parent references.
- Keep metadata context (path/title/heading) in the chunk record; do not duplicate it in
  read output.
- Chunk identity incorporates repo scope, file content and structural location. No
  positional counter is the only identity; location metadata still updates on line
  moves. Store exact line/byte ranges per chunk.
- Separate document and code pipelines: docs/config use heading/paragraph/field structure
  and text-oriented lexical fields. A shared persistent store and unified search
  interface query these logical indexes. Do not require two models or vectors for the
  offline baseline.
- Lexical FTS fields support path, symbol, heading, and body.

## Incremental indexing (master plan section 7)

1. Resolve scope and snapshot; load last complete generation for that scope.
2. Enumerate eligible files and compare content/config/parser fingerprints.
3. Reparse changed files (the embedding step belongs to PR 3).
4. Tombstone deleted/moved records in the new generation; preserve old committed
   snapshots only according to bounded retention policy.
5. Validate ranges, coverage, and manifest consistency.
6. Publish a complete generation transactionally; readers remain on the old one until
   commit.

- Serialize publishers per repo/scope, not all users globally. A failed build must not
  publish a truncated replacement as healthy.
- Persist source/chunk hashes so incremental behavior survives process restarts.
- Incremental and clean rebuilds must produce equivalent evidence/ranking under
  deterministic settings.
- Branch names are mutable aliases; commit hashes are snapshot identity. Worktrees and
  dirty state have separate scopes. Local working-tree mode layers modified/deleted/
  untracked eligible files over a committed snapshot; exact content hashes establish
  freshness. It must shadow old hits for replaced paths, report dirty status, and never
  fabricate commit permalinks for dirty text.
- Search/read default to the agent's declared current scope, not whichever index built
  most recently.
- On read, validate result scope and source hash. A changed working-tree result returns
  `stale_result` with refresh instructions, not unrelated new text. Committed reads stay
  pinned.
- Retention/GC must reference-count shared data and preserve active readers/generations.
- `purge` removes source text/cache for a scope and verifies logical absence; do not
  promise forensic secure erasure of SQLite files or external backups.

## Search and read contracts (master plan section 8)

- Apply repo/snapshot/path/type/lifecycle filters before ranking. Exact path/symbol
  matches take precedence for identifier queries. Lexical FTS supports path, symbol,
  heading, and body fields. Semantic search (PR 3) complements it for conceptual
  queries.
- Deduplicate repeated/sibling ranges and keep a small diversity of files.
- Apply modest, explainable current-doc preference for current-behavior questions;
  preserve history for explicit why/history/plan queries. Similarity and authority are
  separate result fields. Reranking is optional and disabled initially.
- CLI JSON operations (the same service methods MCP exposes in PR 6):
  - `search_project_knowledge`: query, repoId, snapshotId/mode, optional path/role
    filters, maxResults (default 5, cap 20), maxOutputTokens (default 1200),
    continuation cursor.
  - `read_project_knowledge`: opaque result/source ID, expected source hash, requested
    range or bounded parent expansion, maxOutputTokens (default 2500).
  - `project_knowledge_status`: indexed revision, scope, dirty state, lexical/vector
    coverage, staleness, last error, profile and limits.
- Search response: schemaVersion, effectiveScope, generationId, retrievalMode, coverage,
  results, truncated flag, opaque next cursor, and counted/estimated output tokens.
- Each result: sourceId, path, revision/hash, role/lifecycle, range, title/symbol,
  compact excerpt, ranking explanation, optional validated URL. Do not dump embeddings
  or full files.
- Cursors bind to filters/scope/generation and have expiry; reject reuse on a changed
  query.
- Read returns exact text with provenance, range, available parent/neighbor references,
  and any truncation/continuation marker. Opaque IDs are references, not authorization;
  every operation rechecks configured repo scope/permissions. Enforce a server output
  cap in addition to client budget. Count with the configured tokenizer; label
  estimates when none is available.
- No-query/no-match is a first-class response with lexical/filesystem fallback
  suggestions.

## CLI surface added (master plan section 10)

`index --mode working-tree [--paths ...]`, `index --ref HEAD`, `check --fresh`,
`search --query "..." --json`, `read --source-id ... --json`, `status --json`,
`purge --repo ...` (proposed names; not available today).

- `check --fresh` exits nonzero for a missing/stale required generation or unmet
  configured coverage without triggering provider calls; define stable exit-code
  categories and machine-readable status for automation.
- Do not claim a committed index is stale merely because an excluded build output
  changed.
- Affected paths are scheduling hints; they cannot declare unchecked corpus paths
  globally fresh.
- Return GitHub permalinks only from a validated GitHub remote and exact SHA/path/range;
  otherwise return repoId/path/revisionId, not a guessed URL. Line ranges refer to the
  stated snapshot, never silently to latest main.

## Benchmarks (master plan section 11)

- Proposed warm single-file lexical target: p95 <= 250 ms after debounce for files
  <= 100 KiB on declared reference hardware/corpus; report debounce and provider
  latency separately. This is a benchmark target, not a guarantee.
- Run the initial engineering benchmark immediately after this PR's offline CLI behavior
  works: pinned public commits covering docs-heavy, TypeScript, Python, and large
  multilingual monorepo workloads (candidates: TypeScript, VS Code, CPython,
  Kubernetes). Report cold/full discovery/parse/lexical-publication timings, steady
  storage breakdown, and update metrics (no-op, one literal/function/paragraph, line
  insertion, rename/delete, bulk formatting, branch switch, ignored/config changes)
  with p50/p95 save-to-searchable latency. Code runs follow PR 4; semantic modes follow
  PR 3.

## Acceptance criteria (card K2)

- First offline install/init/index/search/read milestone works end to end.
- Structural Markdown: fenced headings, long tables, stable ranges.
- Line-shift reuse: unchanged chunk inputs are not reprocessed; location metadata
  updates.
- Restart persistence: incremental behavior survives process restart.
- Atomic rebuild equivalence: incremental and clean rebuilds produce equivalent
  evidence/ranking under deterministic settings.

## Rollback and limitations

Generated cache is disposable. Retain the previous complete generation when a new build
fails; schema upgrades build into a new namespace rather than mutating the only working
index. Limitation: lexical only — conceptual queries degrade to identifier/path
matching; report retrievalMode and coverage honestly.
